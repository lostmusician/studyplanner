# Test Coverage Report

Generated via `npm run test:coverage` (Vitest + the v8 coverage provider).

## Scope

Only the pure logic layer is unit-tested — `src/lib/` (study-plan computation) and the
top-level files in `shared/` (types, the NUSMods API client, the share-link codec). React
components are verified manually (`npm run dev` + a browser check, per each plan's manual
verification steps), not with component tests — this is a deliberate project convention, not
a gap. Coverage below is scoped to that tested layer only (see `vitest.config.ts`'s
`coverage.include`).

## Notes

All three tested files sit below 80% — none of this is hidden or manufactured, so here's
what's actually behind each number:

- **`shared/nusmods.ts` — 0%.** There is no `nusmods.test.ts`; this file (the NUSMods API
  fetch client) isn't exercised by the suite at all. It's a thin wrapper around `fetch`, which
  is presumably why Task 1/2 didn't target it — testing it would mean mocking `fetch` rather
  than testing pure logic. Legitimate gap, and a reasonable follow-up: a small test with a
  mocked `fetch` for the response-parsing branches.

- **`shared/share.ts` — 70.45% stmts / 54.87% branch (81.48% funcs).** `share.test.ts` only
  exercises the compact v2 codec (`encodeCompactPlan` / `decodeCompactPlan`). The legacy v1
  `encodePlan` / `decodePlan` pair, `buildShareLink`, and `readImportFromHash` are never
  called by any test (confirmed against `share.test.ts`'s imports, which pull in only the
  compact functions), which accounts for the uncovered lines around 119–146 and 196–207.
  `buildShareLink` also reads `window.location`, which needs a DOM/jsdom-style environment
  the current `environment: 'node'` config doesn't provide. Worth a follow-up test for
  `readImportFromHash` (pure string parsing, no DOM needed) since it's the one uncovered
  function most likely to have a real bug (hash-format edge cases).

- **`src/lib/studyPlan.ts` — 68.55% stmts / 44.44% branch (59.21% funcs).** The 19 tests in
  `studyPlan.test.ts` focus on the derived/computed functions — `matchesFulfiller`,
  `courseLevel`, `computeStats`, `computeRequirements`, `computeDoubleCount`,
  `computeTripleCountedCodes`, `computeFocusAreas`, `computeBreadthDepth`, `autoCategoryId`.
  The plan-mutation CRUD helpers are untouched: `createEmptySemesters`,
  `defaultPlanToSemesters`, `upsertModule`, `removeModule`, `isModuleLocked`, `renameModule`,
  and `getCompletedCodesUpTo` all show 0 invocations in `coverage/lcov.info`. These are
  simple, low-branching functions (map/filter over arrays), so the risk they're hiding a bug
  is lower than for the constraint-evaluation logic that's already covered — but they're
  reasonable candidates for a follow-up test pass if this file changes again. Separately,
  `computeFocusAreas` is tested but never with a non-empty `waivedModules` argument (line 255
  uncovered), so the "a waived module counts toward focus-area fulfillment" path is unverified.

None of the above is a defensive fallback masking dead code — it's straightforwardly
untested surface area, concentrated in three places: an untested file (`nusmods.ts`), an
untested legacy code path (`share.ts`'s v1 functions), and untested CRUD helpers
(`studyPlan.ts`). Nothing so far suggests any of it is currently broken; it's simply outside
what Tasks 1–2 chose to cover.
